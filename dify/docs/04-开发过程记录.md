# 开发过程记录（DSL 是怎么来的、调了哪些坑）

> 题目要求提交"运行日志"等验证材料；本文记录**本作品的开发与调试轨迹**，便于核对
> 「Dify 承担核心编排」与「指定技术真实发挥作用」。

---

## 1. 交付物是怎么生产出来的

| 产物 | 生产方式 | 可复现命令 |
|---|---|---|
| Dify DSL（14 节点） | **脚本生成**：`scripts/build_dsl.py` 用节点模板拼出 YAML | `python3 dify/scripts/build_dsl.py` |
| 侧车服务 | 手写 Python（标准库 HTTP + vendor PyMySQL） | `python3 -m app.main` |
| 35 条设定 | `data/lore.json`（JSON，带触发条件字段） | `python3 -m app.seed` |
| 建表 DDL | `data/schema.sql` | 同上 |

为什么 DSL 用脚本生成而不是手搓 YAML：
14 个节点里有 4 段 Python 代码、2 段 LLM prompt、6 个 HTTP body，手写极易出现
"变量引用写错一个字符"的问题；脚本化之后，
`scripts/build_dsl.py` → `scripts/validate_dsl.py` 形成"生成→自检"闭环，
改 prompt / 改逻辑后重跑一次即可，评审也能看懂每个节点在做什么。

## 2. 关键调试记录（都是真实踩过的坑）

### 2.1 Dify 变量引用必须用节点 id，不能用别名 ⚠️ 最致命的一个

初版 DSL 里写的是 `{{#code_state.affection#}}`（别名），结果 Dify 解析不到。
导出过的真实 DSL 里，变量引用形如 `{{#1750000000009.affection#}}`——用的是**节点 id**。

修法：生成器里保留可读别名，最后由 `resolve_aliases()` 统一替换成节点 id；
再写 `scripts/validate_dsl.py` 扫描所有模板引用，逐个核对"目标节点是否存在、字段是否存在"。

```
$ python3 dify/scripts/validate_dsl.py
✅ DSL 自检通过
```

### 2.2 seekdb 混合检索 DSL 的三个细节

| 现象 | 原因 | 处理 |
|---|---|---|
| `1210 Invalid argument` | `"must": []`（空数组）不被接受 | 没关键词时整段省略 `query` 字段 |
| 过滤子句偶尔不生效 | 不同小版本对 `terms`/`range` 支持不一致 | 只用最稳的 `term`/`range`，并在 Python 侧再过滤一次兜底 |
| 中文全文检索命中不了 | 默认分词器按空格切 | `FULLTEXT INDEX ... WITH PARSER ngram` |

### 2.3 向量字面量格式

seekdb 的向量必须写成字符串字面量 `'[0.1,0.2,...]'`，直接写 `0.1,0.2` 会报 `1210 Invalid argument`；
长度必须等于列维度（1536，对齐 MiniMax `embo-01`）。

### 2.4 MiniMax 的 embeddings 不是 OpenAI 兼容格式

MiniMax 用 `{"texts": [...]}`、返回 `{"vectors": [...]}`；
而 PowerContext / Dify 的 OpenAI 兼容客户端只会发 `{"input": [...]}`、只认 `{"data":[{"embedding":...}]}`。
解法：侧车提供 `/v1/embeddings` 薄代理，把 MiniMax 包成 OpenAI 形状（`backend/app/main.py`）。

### 2.5 PowerContext 连远端 seekdb 的重启坑

现象：第一次启动正常，**重启**报
`1050 Table 'memories' already exists` → memory service 不可用 → health 变 `degraded`。

定位：驱动层用 SQLAlchemy 的 `inspector.has_table()` 判断表是否存在，
对 seekdb 的 `information_schema` 兼容不好，**误判表不存在**，于是重复建表。

处理：`scripts/init_powercontext.py` 在每次启动前删掉 `memories` / `user_profiles`，
让 PowerContext 自己重建（演示用记忆随后由 `seed.py --memory` 写回）。运行说明里已写死这一步。

### 2.6 本机网络环境（影响部署可复现性）

| 问题 | 实测 | 绕行 |
|---|---|---|
| Docker Hub 拉不动 | `docker.1panel.live` 偶发 `TLS handshake timeout` | 改用 `docker.m.daocloud.io` 拉完再 `docker tag` 回官方名 |
| PyPI 全线不通 | pypi.org / 阿里 / 清华 / 腾讯均超时 | 侧车改成**零第三方依赖**（标准库 + vendor PyMySQL，MIT） |
| HuggingFace 不通 | API 超时 | `HF_ENDPOINT=https://hf-mirror.com`（实测 200）；或改用 OpenAI 兼容 embedding |

### 2.7 Dify 1.18 的 DSL 格式变化（导入即报错的三个点）

| 现象 | 原因 | 处理 |
|---|---|---|
| `body.type should be 'none', 'form-data', 'x-www-form-urlencoded', 'raw-text', 'json' or 'binary'` | 老版本叫 `json-body`，1.18 改名成 `json` | 生成器里改成 `type: json` |
| `json body type should have exactly one item` | `type=json` 时 `body.data` 只能有**一条**，value 是完整 JSON 文本 | 生成器把整段 body 序列化成一条文本（嵌套对象用 `@@RAW@@` 原样插入） |
| 节点参数里的数字全部变成字符串 | DSL 模板插值后都是字符串 | 侧车统一做 `int/float` 转换（`_as_int`） |

### 2.8 Dify 1.18 控制台 API 的几处"反直觉"

| 现象 | 原因 | 处理 |
|---|---|---|
| 登录报 `Invalid encrypted data` | `password` 字段要求 **base64** 编码（`libs/encryption.py`） | 客户端登录前 base64 |
| 首次 setup 报 `not_init_validated` | 1.18 增加了一步"初始化校验" | 先 `POST /console/api/init {password: INIT_PASSWORD}` 再 setup |
| 密码报 422 | 账号密码需**字母+数字且≥8位**；邮箱需合法域名 | 用 `you@example.com` + 强密码 |
| 导出接口返回的是 zip 不是 yaml | 1.18 的 `export?mode=yaml` 返回 `.ifpkg` | 解包取 `app.yaml`（`dify_ops.py export` 已处理） |
| 插件列表报 "Failed to request plugin daemon" | `.env` 缺 `PLUGIN_DAEMON_URL` | 补上并重启 api/worker |
| 添加模型报 `does not have provider_credential_schema` | OpenAI-API-compatible 是"自定义模型"型插件，要走 `models/credentials` 而不是 provider 级 credentials | 改用 `/model-providers/<p>/models/credentials` |
| 凭证报 `Variable context_size should be string` | 凭证字段必须是字符串 | 全部转成字符串再提交 |

### 2.9 提交前复核又抓到的两个真 bug

| bug | 现象 | 根因 | 修复 |
|---|---|---|---|
| `schema.sql` 里 `USE nightstore;` 写死 | 改 `.env` 里的 `DB_NAME` 后，**表建到了别的库里**（数据写不进目标库，而脚本还报告"成功"） | DDL 里硬编码库名 | `ensure_schema()` 里把 `USE xxx;` 动态替换为实际 `DB_NAME`；已用独立库 `nightstore_dbnames` 验证 35 行正确落库 |
| embedding 不可用时直接抛异常 | 账户余额不足/Key 失效 → `app.seed` **整个失败**，评委无法复现 | 只报错不降级 | 侧车自动降级为本地确定性向量（打印一次性警告，`/health` 里 `embed_effective` 显示降级状态），流程不中断；换可用 Key 后重跑 seed/reindex 恢复 |

### 2.10 离线自检模式（scripts/mock_llm.py）

复核时发现本机 MiniMax 额度耗尽（`1008 insufficient balance` / `429 Token Plan`），
于是加了一个**OpenAI 兼容的 Mock 模型服务**（仅标准库，支持 SSE 流式），
把 Dify 的模型凭证临时指向它，即可验证整条链路——这同时说明：
**作品不绑定 MiniMax**，任何 OpenAI 兼容模型（DeepSeek / Qwen / vLLM）都能跑。

> 顺带踩到：Dify 的 LLM 节点默认用**流式**请求，Mock 必须返回 SSE 分片，否则节点拿到空文本。

### 2.11 Dify 侧配置

- 模型供应商用 **OpenAI-API-compatible** 插件（`langgenius/openai_api_compatible/openai_api_compatible`），
  端点填 `https://api.minimax.chat/v1`，模型名 `MiniMax-M2.5`——评委换成 DeepSeek / Qwen 也只需改这一处。
- Dify 容器访问宿主机的侧车(8090)与 PowerContext(8848)：`docker-compose.override.yaml` 里给
  api/worker/web/plugin_daemon 加 `extra_hosts: ["host.docker.internal:host-gateway"]`。
