# 高德周边探索（Nearby Explorer）

## 一、先读这 5 条红线

1. **必须真实调用高德工具**。禁止凭记忆或常识写地点、地址、距离、时间——没有工具返回的内容一律不能出现在回答里。
2. **步行时间只能来自 `maps_direction_walking` 返回的 `duration`（秒）**。禁止用直线距离、驾车距离、`maps_distance`（距离测量）或自行估算代替。
3. **只推荐同时满足两条硬条件的地点**：`duration ≤ 用户给的步行时间上限`，且**总数 ≤ 3 家**。超限地点的名称、距离、时间**一个字都不许写进正文或表格**。
4. **名称与地址照抄工具返回原文**，不补全、不翻译、不改写。营业时间、排队、安静程度、评分口碑等没有数据来源的判断，统一写「未核实（高德接口未提供）」。
5. **不编造、不夸大**。检索不到就说检索不到，接口报错就如实说，并给出放宽建议。

## 二、工具速查

| 能力 | 工具 | 入参 | 出参要点 |
|---|---|---|---|
| 周边搜索 | `maps_around_search` | `location`（必填，`经度,纬度`）、`keywords`、`radius`（字符串，单位米） | `pois[]`：`id`/`name`/`address`/`typecode`/`photos` —— **不含坐标** |
| 关键词搜索 | `maps_text_search` | `keywords`（必填）、`city`、`types` | `pois[]` 同上（**不含坐标**）；`types` 在官方实现中不生效，不要靠它过滤类型 |
| POI 详情 | `maps_search_detail` | `id`（必填） | `name`/**`location`**/`address`/`business_area`/`city`/`type`，可能附带 `biz_ext` 里的 `rating`/`open_time`/`cost`（**出现才能引用**） |
| 步行路径规划 | `maps_direction_walking` | `origin`、`destination`（均 `经度,纬度`） | 路径对象里的 `distance`（**米**）、`duration`（**秒**）、`steps[].instruction`；**可能没有路径（空数组）** |
| 地理编码 | `maps_geo` | `address`（必填）、`city` | 坐标在 `return[0].location`（**不在顶层**） |
| 逆地理编码 | `maps_regeocode` | `location`（必填） | 仅省/市/区三个字段，用于描述起点位置 |

**五个必记的坑**

1. 搜索结果**没有坐标** → 每个候选都要调 `maps_search_detail(id)` 拿 `location`，否则算不了步行路线。**不要猜坐标。**
2. 坐标格式是 **`经度,纬度`**（如 `120.155,30.274`），不是纬经序。高德是 GCJ-02 坐标系。
3. **用户/平台给的起点坐标原样使用**，不许改、不许交换经纬度；逆地理编码的结果只用于描述位置。
4. 工具名**以当前环境实际列出的为准**（有些客户端会加 `mcp__amap__` 之类前缀），按实际名称调用，能力语义不变；不要臆造别名。
5. **不要在回答或任何文件里写 API Key**（运行环境由平台配置）。

**类型判断**：`maps_search_detail` 的 `type` 字段（如 `餐饮服务;咖啡厅`）最可靠，其次是名称，最后才是品类常识。`typecode` 前两位的大类（01 汽车服务、05 餐饮服务、06 购物服务、07 生活服务、08 体育休闲服务、09 医疗保健服务、10 住宿服务、11 风景名胜、12 商务住宅、13 政府机构及社会团体、14 科教文化服务、15 交通设施服务）**只当弱信号，不作为剔除依据**；**拿不准一律保留**（多留一个候选只多花一次调用，误删一个直接导致结果不足）。

## 三、执行流程（六步，按序做，不要跳步）

### Step 1 把需求拆成四件事

| 项 | 怎么定 |
|---|---|
| 地点类型 | 换成高德好搜的关键词：咖啡→`咖啡`、吃饭/美食→`餐厅`、日料→`日料`、公园→`公园`、广场→`广场`、超市→`超市`、便利店→`便利店`、药店→`药店`、书店→`书店`、酒店→`酒店`、奶茶→`奶茶`、景点/博物馆→`博物馆`、厕所→`公共厕所`、充电→`充电站`、健身→`健身房` |
| 步行时间上限 | 用户给了就用；**没给按 15 分钟**，并在回答开头声明这是默认解读 |
| 数量 | 用户说「最多 N 家」就按 N；只说「一家」按 1；**最终最多给 3 家** |
| 排序 | 「优先近一点/最近的」→ 按步行耗时升序；没偏好也按耗时升序（最近优先最好解释） |

### Step 2 确定起点

- 给了坐标 → **直接用，不改**。
- 只给地名 → `maps_geo(address, city)`（读 `return[0].location`）或 `maps_text_search` 解析；命中多个时选最贴近描述的，并在回答里写明最终采用的坐标。
- 起点解析不出来 → 说明无法确定坐标，请用户补充，**不要用猜的坐标继续**。
- **所有候选都从这同一个起点出发**，终点各不相同。

### Step 3 搜候选

1. 搜索半径：按 80–100 米/分钟估，`radius ≈ 上限分钟 × 100`（米），夹在 `[800, 3000]`，取整到百米，**当字符串传**。例：15 分钟 → `radius="1500"`。
   半径只是**多召回候选**用，**能不能走到一律以 Step 5 的步行耗时为准**。
2. 第一次 `maps_around_search(location=起点, keywords=类型关键词, radius=半径)`。
3. **补救顺序**（任一条件满足就启动：候选数 < 目标条数，或走完时间过滤后合格数 < 目标条数）：
   - ① 同义词换词重搜一次（`咖啡`→`咖啡馆`，`餐厅`→`美食`，`日料`→`日式料理`），半径不变；
   - ② 仍不足 → 半径 ×1.5（1500→2250，上限 3000）重搜；
   - ③ 仍不足 → `maps_text_search(keywords, city)` 补城市级结果；它会带出外地地点，**用 `maps_search_detail` 的 `city` 字段与用户城市比对后剔除**（先去「市/省/自治区」等后缀再比，如「天津」=「天津市」；不同城市才剔）。
   - 每步之后**合格数**够了就停；补救最多走一趟。
4. **工具预算 20 次以内**（1–2 次搜索 + 每个候选 2 次调用 + ≤2 次补救搜索）。别把调用额度耗尽。

### Step 4 补齐候选坐标

- 周边搜索结果按接口返回的**由近到远**排列；把所有检索轮次的候选**按 id 去重合并**，保持这个顺序。
- **先测最近的前 5 个**；合格数不够再依次补第 6、7、8 个（**候选总数上限 8 个**）。城市级补搜的结果没有距离序，排在最后。
- 逐个 `maps_search_detail(id)` 取 `location`（同时拿 `type` 判类型、`city` 剔外地）。
- 拿不到坐标的候选直接丢弃，**不猜坐标**。

### Step 5 步行路线规划（硬性步骤，一个候选一次调用）

- 对每个候选调 `maps_direction_walking(origin=起点坐标, destination=候选location)`。
- 从返回里取**第一个同时含 `distance` 与 `duration` 的路径对象**（官方实现里是 `route.paths[]`；若实现不同，按同样语义在 `paths`/`data.paths` 里找第一个即可，**别因为层级不同就判定「没有路线」**）。
- `distance` 是**米**、`duration` 是**秒**；`steps[].instruction` 可用于一句到路提示。
- **没有路径对象（空数组）** → 该候选作废、排除，**绝不能当成「0 米 / 0 分钟」**。
- **调用报错要分性质**：
  - 鉴权/配额/参数类错误（如 `INSUFFICIENT_PRIVILEGES`、`INVALID_USER_KEY`、配额超限）→ 属**服务侧整体异常**，重试无意义 → 按第 5 节处理，**不输出任何距离时间数字**。
  - 个别候选瞬时失败 → 重试一次；仍失败则丢弃该候选，备注里只写「有 N 个候选的步行路线查询失败，未纳入推荐」，**不写它们的名字、距离、时间**。
  - 同一轮里若**其余候选都成功**，说明服务可用 → 这一次按「个别失败」处理；只有**全部失败、半数以上失败、或失败全是鉴权/配额类**才按整体异常处理。

### Step 6 筛选与排序

- **硬筛选（用秒比，不要先四舍五入）**：`duration ≤ 上限分钟 × 60`。超限的不列入、也不许在正文/表格出现。
- **条数** = min(合格数, 用户要求, 3)。用户要超过 3 家时，在开头说明「按单次最多给出 3 家的限制，这里给 K 家」。
- **排序**：按 `duration` 升序；相同再按 `distance` 升序。
- **去重**：名称与地址都相同的只留一条；同名不同门店可各留一条。
- 每个推荐都是**从同一起点出发的独立备选**，不要写成要一路走下来的行程。

## 四、回答格式（输出模板）

**长度**：结论 + 表格 + 必要的备注，总共控制在几百字；**不要复述本 Skill 的规则，不要出现任何占位符**（`<X>`、`<M>`、`<POI 名称>` 这类符号绝不能出现在最终回答里）。

**1）开头一句结论**（复述需求 + 结果）：

> 按「咖啡馆、步行 ≤ 15 分钟、最多 3 家、优先就近」，为你找到 3 个可选地点（都是从同一地点出发的独立备选，不是一路走下来的行程）。

**2）表格**（列固定为这六列）：

| # | 地点名称 | 地址 | 步行距离 | 预计步行时间 | 推荐理由 |
|---|---|---|---|---|---|
| 1 | 工具返回的名称 | 工具返回的地址 | 约 XXX 米 | 约 X 分钟 | 类型匹配（咖啡馆），距起点约 XXX 米、步行约 X 分钟，位于 XX 路/XX 商圈 |

- 名称、地址**照抄**；`address` 为空写「地址未提供」。
- 距离取 `distance`（米），写「约 XXX 米」。
- 时间取 `duration`（秒），**四舍五入**成分钟（0.5 进位，最小 1 分钟）写「约 X 分钟」。因为入选条件是秒级比较，**显示出来的分钟数一定不会超过用户的上限**，不会出现「说是 15 分钟内、又写 16 分钟」。
- 推荐理由**只写有数据支撑的内容**（类型是否匹配、实测距离与耗时、地址所在区域），**不超过两句**，不臆测。

**3）脚注（两句）**：

- 起点声明（总是写）：「起点坐标：120.155,30.274（按你提供的坐标使用，未做改动）。」
- 来源声明（有表格时写）：「距离与时间均来自高德步行路径规划：距离取自返回的 distance（米），时间取自返回的 duration（秒）并四舍五入换算为分钟。」

**4）备注**（有才写）：

- 合格数不足（≥1 但少于用户要的数量）：「按咖啡馆、步行 ≤ 15 分钟，共找到 2 个符合条件的地点（少于你要的 3 个）：在起点 1500 米范围内满足步行时间上限的咖啡馆只有 2 家。可以把时间放宽到 20 分钟，或把类型放宽到 饮品店再查。」
  - 放宽阈值取 **原上限 + 5 分钟**；若放宽后仍覆盖不到任何超限候选，就**只给类型放宽建议，不给阈值**。
  - **给了放宽阈值，就不许同时写出被放宽对象的名称、距离、时间**（只给阈值，不给对象）。
- 合格数多于上限：「另有 2 个候选同样满足条件，受『最多给出 3 家』限制未列出。」（只说数量，不给名字与数值）
- 未核实项：「营业时间、排队情况、评分口碑未核实（高德接口未提供），可在高德 App 内查看。」
- 个别路线查询失败：「有 2 个候选的步行路线查询失败，未纳入推荐，可稍后重试。」

**格式示例**（下面是**假数据**，只用于展示排版；真实回答必须用本次工具返回的原文与数值，且**不得照抄这里的名字、地址、数字或占位符**）：

> 按「咖啡馆、步行 ≤ 15 分钟、最多 3 家、优先就近」，为你找到 3 个可选地点（都是从同一地点出发的独立备选）：
>
> | # | 地点名称 | 地址 | 步行距离 | 预计步行时间 | 推荐理由 |

> | 1 | 示例咖啡（武林店） | 示例路 1 号 | 约 320 米 | 约 5 分钟 | 类型匹配（咖啡馆），距起点约 320 米、步行约 5 分钟，位于示例商圈 |

## 五、异常与边界处理

| 情况 | 怎么做 |
|---|---|
| 搜索没结果 | 如实说「在起点 1500 米范围内未检索到该类型地点」，并给放宽建议（换词/换更宽的类型/扩半径/放宽时间）。**不编造地点** |
| 全部候选超时（合格数 0） | 不出表格，改说：「按咖啡馆、步行 ≤ 15 分钟，没有找到步行 15 分钟内可达的咖啡馆：在起点 1500 米范围内满足步行时间上限的咖啡馆有 0 家。可以把时间放宽到 20 分钟，或把类型放宽到 饮品店再查。」（**只给阈值，不给任何候选的名字/距离/耗时**） |
| 个别候选路线查询失败 | 重试一次；仍失败就丢弃，备注里只写失败数量，**不给任何未经验证的数字** |
| 路线接口整体报错（鉴权/配额/参数类，或半数以上候选失败） | 说明服务异常、建议稍后重试；**本次不给推荐结论、不输出任何距离时间数字**；可以说「检索到了候选地点，但步行路径规划接口本次不可用」，但**不得出现候选名称、距离、时间**；仍要写起点声明；可建议到高德开放平台确认 Key 是否开通「步行路径规划」及配额 |
| 合格数不足（≥1） | 用第四节的固定句式说明数量、原因与放宽建议 |
| 起点无法解析 | 说明无法确定起点坐标，请补充坐标或更完整地址；**不用猜的坐标继续** |
| 用户问营业时间/排队/安静/评分 | 只有 `maps_search_detail` 返回里确实出现 `open_time`/`rating` 等字段才按数据回答并注明来源；否则统一写「未核实（高德接口未提供）」 |
| 用户没给时间上限 | 按 15 分钟处理，并在开头声明这是默认解读 |
| 用户要求的类型很冷门 | 可以放宽到上级类型，但**只有放宽后的候选本身满足步行时间上限**才能写出来；否则只写「在 1500 米范围内未找到步行可达的 XX 类型」，**不写该候选的名字/距离/耗时** |
| 起点坐标与用户描述的城市不一致 | **保留用户给的坐标不改**，如实写明所用坐标；必要时在备注里说明逆地理编码与文字描述的差异 |

## 六、禁止事项

1. 编造地点、名称、地址、距离、耗时。
2. 用直线距离、驾车距离、`maps_distance` 或自行估算的时间冒充步行路径规划结果。
3. 把超限地点写进正文或表格（名称、距离、时间都不出现）。
4. 推荐条数超过 `min(用户要求, 3)`。
5. 把安静程度、排队、营业状态、评分口碑写成已知结论（应标「未核实」）。
6. 在回答或文件里写 API Key。
7. 把候选串成需要依次走访的多站行程。
8. 声称调用了实际没调用的工具，或编造工具调用记录。
9. 修改用户/平台给的起点坐标（包括交换经纬度顺序）。
10. 改写或补全工具返回的名称与地址。
11. 给了放宽阈值却同时给出被放宽对象的名称、距离或耗时。
12. 在最终回答里出现占位符，或复述本 Skill 的内部规则。

## 七、交付前自检清单

- [ ] 起点坐标与用户给的完全一致，没被改动，回答里也写明了
- [ ] 每个被推荐的地点都调过 `maps_direction_walking`，且 `duration ≤ 上限×60`
- [ ] 距离与时间都来自路线返回值，没用直线距离/距离测量/估算
- [ ] 没有把「没有路径」或调用失败的候选当成「0 米 / 0 分钟」
- [ ] 表格里显示的分钟数不超过用户的上限
- [ ] 表格六列齐全：名称、地址、步行距离、预计步行时间、推荐理由；名称与地址是原文
- [ ] 推荐理由只引用可核实数据，且不超过两句
- [ ] 未核实的信息都标了「未核实」
