# 一页技术说明

## 1. 要解决的问题

AI 开发助手修改代码时，需要同时知道三件事：**当前应遵守哪些规格**、**应该修改哪些代码**、**如何验证结果**。这三类资料分散在规格文档、源码和测试里，且会随时间变化。规有所依（SDD Context Module）把"为一个开发任务组装上下文"这件事做成一个可重复、可审计、可跨会话续接的模块。

## 2. 模块结构

```
                         ┌──────────────────────────────────────────┐
   规格 Markdown ────►   │  sddctx ingest                            │
   Python 源码    ────►   │  解析编号规格条目 / 代码符号 / 测试函数      │
   pytest 测试     ────►   └───────────────┬──────────────────────────┘
                                         │ SQL INSERT / DELETE
                                         ▼
                         ┌──────────────────────────────────────────┐
                         │  内嵌 seekDB（工程资料索引）               │
                         │  sdd_documents / sdd_specs /               │
                         │  sdd_code_symbols / sdd_tests              │
                         └───────────────┬──────────────────────────┘
                                         │ 词法匹配（参数化 LIKE）
                                         ▼
   开发任务描述 ────────►  ┌──────────────────────────────────────────┐
   --target-spec SPEC-004 │  sddctx context                           │
                         │  ① 命中规格条目                            │
                         │  ② 规格编号 → 关联代码符号（doc 引用）      │
                         │  ③ 规格编号 → 关联测试（covers 字段）       │
                         │  ④ 标注目标测试 / 回归测试                 │
                         │  ⑤ 补齐工程约定与缺失类型                  │
                         └───────────────┬──────────────────────────┘
                                         │ 上下文 JSON + prompt
                                         ▼
                         ┌──────────────────────────────────────────┐
                         │  sddctx apply                             │
                         │  → MiniMax（真实调用，保存请求与响应）      │
                         │  → unified diff（上下文匹配式应用）        │
                         └───────────────┬──────────────────────────┘
                                         ▼
   目标测试 / 回归测试 ─►  ┌──────────────────────────────────────────┐
                         │  sddctx verify（命令、退出码、日志）        │
                         └───────────────┬──────────────────────────┘
                                         │ 任务状态
                                         ▼
                         ┌──────────────────────────────────────────┐
                         │  PowerContext Server（任务状态持久化）      │
                         │  Scope / Memory：已完成、待办、验证结果     │
                         │  后端：内嵌 seekDB                         │
                         └──────────────────────────────────────────┘
```

## 3. 上下文选择方式

选择分两段：**数据库负责召回，模块负责关联与排序**。

**第一段（数据库侧）** —— 所有候选行都由参数化 `LIKE` 在 seekDB 中筛出，SQL 语句与返回行数记录在 `artifacts/db/*.sql.txt`：

1. `sdd_specs`：按 `spec_id`、`title`、`body` 匹配任务关键词与任务点名的规格编号；
2. `sdd_code_symbols`：按 `symbol`、`path`、`doc`、`signature` 匹配，并额外召回 `doc` 中引用了任务规格编号的符号；
3. `sdd_tests`：按 `name`、`path`、`purpose`、`covers` 匹配，并额外召回 `covers` 含任务规格编号的测试；
4. `sdd_documents`：取相关文件的完整文本，供补丁生成时对齐工程约定。

**第二段（模块侧）** —— 在召回结果上建立规格与代码、测试之间的引用关系并排序：

- 规格条目被显式点名时加权（+5），被任务关键词命中时按命中数加权；
- 代码符号的 docstring 引用了命中规格时加权（每次引用 +2），因此实现某个规格的函数会被优先选中；
- 测试的 `covers` 命中目标规格时加权（+3），并标记 `role=target`；只覆盖"必须保持"规格的测试标记 `role=regression`；
- 规格正文提到但工程中尚不存在的错误类型（如 `InvalidTierError`）会被单独列出，作为"本次必须新增"的提示，避免生成只导入不定义的代码。

任务文本里的规格范围写法（`SPEC-001 ~ SPEC-003`）会被展开成完整编号集合。

## 4. 三项技术的分工

| 技术 | 承担的作用 | 落点 |
| --- | --- | --- |
| **seekDB** | 存放工程资料与索引：文档全文、规格条目、代码符号、测试函数；所有上下文召回都在 SQL 中完成 | `src/sddctx/schema.py`、`src/sddctx/db.py`、`src/sddctx/ingest.py`、`src/sddctx/retrieve.py` |
| **MiniMax** | 依据检索出的上下文完成本次任务的真实代码修改，返回 unified diff；请求、响应、token 用量全部留档 | `src/sddctx/minimax_client.py`、`src/sddctx/patching.py` |
| **PowerContext** | 保存任务进展：Scope 绑定、已完成事项、待办事项、目标测试与回归测试的退出码；模块重启后通过 Server API 读回并写进下一次提示 | `src/sddctx/taskstate.py`、`scripts/start_server.sh` |

三者之间的边界是清晰的：**seekDB 管资料，PowerContext 管状态，MiniMax 管改代码**。模块本身只做编排、检索与记录。

## 5. 状态复用的闭环

1. `sddctx apply` 完成后写入一条 `sdd-task-state` 记忆：任务、阶段、已完成、待办、补丁文件路径、上下文覆盖的规格编号；
2. `sddctx verify` 写入验证结果：目标测试与全量测试的命令、退出码、日志路径；
3. 下一次运行（哪怕是重启后的新进程）先 `resolve_scope` → `load_task_state`，把保存的状态拼进提示词，助手在已有进展上继续，而不是从头再做；
4. PowerContext Server 自身的状态存放在内嵌 seekDB 中，Server 重启后状态仍在（`scripts/stop_server.sh` + `scripts/start_server.sh` + `sddctx state show` 即可复核）。

## 6. 关键设计取舍

| 取舍 | 选择 | 原因 |
| --- | --- | --- |
| 检索放在数据库还是代码里 | 召回放数据库，排序放代码 | 题目要求"查询、检索结果用于构造上下文"；数据库侧过滤让 SQL 记录可核查，排序规则复杂，放模块内更易维护 |
| 规格与代码的关联方式 | 依赖 docstring 与测试名中的规格编号 | 不引入额外标注文件，规格编号本身就是稳定契约；导入时自动提取，人工维护成本为零 |
| 补丁应用策略 | 以上下文匹配为准，行号仅作提示 | 生成式模型给出的 hunk 行号常与文件不符；`patch(1)` 同样以上下文定位，应用成功率显著更高 |
| 状态存储位置 | PowerContext（后端内嵌 seekDB） | 题目要求状态"在后续运行中读取、使用"；用 PowerContext 才能体现上下文管理系统的价值，而不是自建一个状态表 |
| 业务工程选择 | 自建小型订单筛选工程 | 需要"修改前失败、修改后通过"的干净对照，且不触碰已提测的任何代码 |
